# YAML provisioning and GitHub login

Set `ASTRBOT_PROVISIONING_FILE` to a UTF-8 YAML file and restart AstrBot. This optional fork feature manages dashboard authentication and provider sources/models without changing upstream JSON/database storage. With no file configured, upstream behavior is unchanged.

```yaml
version: 1
auth:
  password_login_enabled: false
  github:
    client_id: !env GITHUB_CLIENT_ID
    client_secret: !env GITHUB_CLIENT_SECRET
    redirect_uri: https://astrbot.example.com/api/v1/auth/github/callback
    allowed_organizations: [your-organization]
    allowed_users: [your-github-login]
providers:
  sources:
    - id: openai
      provider: openai
      type: openai_chat_completion
      provider_type: chat_completion
      enable: true
      key: [!env OPENAI_API_KEY]
      api_base: https://api.openai.com/v1
      timeout: 120
  models:
    - id: openai/gpt-4.1
      provider_source_id: openai
      model: gpt-4.1
      enable: true
```

`providers.sources` and `providers.models` use the existing `provider_sources` and `provider` entry formats. Omit `providers` to retain WebUI-managed providers. When present, **both lists replace the complete runtime lists**; empty lists intentionally remove all runtime providers. Export and review your existing lists before enabling this block. Duplicate IDs and dangling model references are rejected. Provider-specific options keep their upstream meanings. Default-model selection, session overrides, chat rules, plugins and other state remain upstream-managed.

YAML is loaded once per process. Restart to apply changes. A Kubernetes ConfigMap generated by Kustomize causes a rollout when its content changes. Changing an environment Secret also requires a restart. WebUI/API provider mutations are rejected while YAML owns providers; read and connection-test endpoints remain available. The original JSON provider lists are retained on disk, and unrelated settings remain writable. Removing the provisioning block restores those original lists on restart. Resolved YAML provider secrets are not written into `cmd_config.json`; authenticated administrators can still inspect provider settings through the existing API.

`!env NAME` resolves an explicitly named environment variable as a string. Missing/empty variables, malformed YAML, duplicate keys, unsupported schema versions and unknown provisioning fields fail startup. Do not commit secrets in YAML. Provider entries intentionally retain upstream's flexible option dictionaries.

## GitHub OAuth App

Create a GitHub **OAuth App**, not a GitHub App, and set its authorization callback URL to the exact `redirect_uri`. Use HTTPS in production. For local testing, `http://127.0.0.1:6185/api/v1/auth/github/callback` is supported; visit the WebUI using the same hostname. The reverse proxy must preserve the public URL and forward to AstrBot. No proxy identity headers are trusted for login.

Access is granted when the authenticated GitHub login matches `allowed_users` **or** the user has active membership in at least one allowed organization. Names are case-insensitive. Empty allowlists deny everyone. Pending organization invitations do not qualify. Membership checks use the authenticated membership API, including private memberships. The app requests `read:org`; organization OAuth restrictions or SSO may require additional approval. GitHub errors fail closed.

Every allowed user gets **full dashboard administrator access**. This is not an RBAC system. Sessions use the immutable GitHub numeric user ID as `github:<id>`; user allowlists use GitHub login names, so review them after renames. Allowlisted users bypass the organization requirement intentionally.

The browser flow uses state bound to an HttpOnly cookie, PKCE S256, and short-lived single-use state/session tickets. GitHub access tokens stay on the backend and are not persisted. Tokens are not placed in redirect URLs. AstrBot sessions expire after one hour; membership/allowlist changes take effect at the next login, so a previously issued session may remain valid for up to one hour. Restarting drops pending login attempts. Use one AstrBot process/replica (the upstream SQLite deployment model); pending state is in memory.

`password_login_enabled: false` disables password login, initial-account setup and desktop auto-login, and rejects previously issued local dashboard sessions. Existing scoped API keys continue to work (for example, Alertmanager). Short-lived plugin asset tokens remain restricted to their original asset paths. `true` keeps upstream password authentication available alongside OAuth. GitHub authentication relies on GitHub's own MFA; AstrBot's password TOTP flow does not apply.

For recovery from a bad allowlist or GitHub outage, edit the YAML through the deployment administrator account and restart. To restore password login, set `password_login_enabled: true` and use upstream's password reset procedure if necessary. No unauthenticated fallback is opened automatically.
